Expert100 EP32 需求与候选方案

UBX / 非 UBX 双场景评审稿
日期：2026-11-17 状态：需求整理，推荐方案尚待评审 适用分支：feat/Eexpert100-ep32、feat/Expert100-ep32-main

1. 文档约定与目标

本方案将内容分为三类：已确认需求表示用户已经明确提出； 推荐方案表示基于当前代码和目标配置给出的首选路径； TBD表示尚未决策，备选方案不等于已批准实现。

主要使用方为算子开发、精度验证和性能验证人员。完成条件是：两个场景使用一致的需求定义，在目标拓扑和配置下完成新流程，并满足最终确认的精度标准。

核心目标：新增 GELU，复用并扩展 Quant 前 Logits 加权，TopK 最大支持 32，逐步覆盖 8 卡单机、16 卡单机和 32 卡跨机，支持 A8W4、A8W8，同时控制 UBX 与主干代码差异。

3. 当前实现基线与主要差距

以下现状来自当前 UBX 分支 feat/Eexpert100-ep32。非 UBX 的 main 基线需在详细设计前单独核对，不能默认两者现状完全一致。

能力当前实现与目标的关系
激活 公共 API 仅开放 SwiGLU；激活内部使用 FP32 计算并输出 BF16。 GELU 需要新增，不是替换已有 GELU 公式。
Logits / TopK 加权 topk_weights_type=0 在 GMM2 后加权；topk_weights_type=1 已在 SwiGLU 后、Quant 前加权。 目标前移路径已有实现，可扩展复用，不需要从零迁移。
量化 采用 MX 量化，每 32 个元素共享 E8M0 Scale；公共 API 支持 FP8×FP4 和 FP8×FP8。 优先继承现有量化语义。
TopK / 拓扑 MTE 入口允许 TopK≤32；URMA 入口限制 TopK≤8、EP4/8/16，且单卡 Token 上限为 16384。 目标 TopK25/32、EP32 和 39280 Token 是否要求 URMA 全支持，需要明确后端范围。
精度判定 Golden 当前使用统一的混合误差规则，没有按 A8W4/A8W8 分别定义阈值。 先沿用现有规则，是否按精度分别设定阈值留待验证数据决策。

代码依据： api.py L76–112； README.md L116–129； swiglu_activation.hpp L71–99； forward.cpp L651–675； mega_moe_arch35.hpp L152–178； golden.py L243–274。

4. 目标计算流程

已确认需求 Logits 专家加权由 Finalize 前移至 Quant 前，Finalize 不再重复加权。

原默认流程：
GMM1 → SwiGLU → BF16/MX Quant → GMM2 → Logits/TopK 加权 → Finalize

本需求目标流程：
GMM1 → GELU → Logits/TopK 加权 → Quant → GMM2 → Finalize（不再加权）

推荐数据路径 沿用当前前移模式的数值顺序：

GMM1 → GELU（FP32 内部计算）→ FP32 Logits 加权 → BF16 → MX Quant → GMM2 → Finalize
两种加权位置因量化顺序不同，不要求结果逐位一致。验收应分别建立对应 Golden，不能用旧的 GMM2 后加权结果直接作为新流程的唯一真值。

5. 功能需求与候选方案

FR-01 GELU 激活

  • 新增 GELU 配置，执行位置为 GMM1 后、Logits 加权前。
  • 保留现有 SwiGLU 能力，不因新增 GELU 改变原配置的默认行为。
  • UBX 与非 UBX 使用相同公式、参数定义和 Golden 语义。
  • 不支持的激活名称或参数组合应明确报错，不允许静默回退到 SwiGLU。

D1：GELU 输入结构 TBD，开发前确定

方案 A：标准单路 GELU 推荐

GMM1 直接输出待激活结果，再逐元素执行 GELU。与目标 GMM1 K/N=4096/1536、GMM2 K/N=1536/4096 直接对应。

需要新增单输入激活处理，并核对权重布局及 tiling 对 gate/up 双路的假设。

方案 B：门控 GEGLU

GMM1 输出 gate/up 两路，执行 GELU(gate) × up。仅当目标模型权重本身就是门控结构时采用。

该方案的 GMM1 物理输出宽度需要重新核算，不能直接沿用方案 A 对目标 K/N 的解释。

D2：GELU 公式 TBD，开发前确定

方案规则适用条件
A：精确 erf 版（推荐基线）0.5x[1 + erf(x/√2)]；Kernel 与 Golden 均以此为准。目标模型未指定近似方式时，先消除公式歧义；需评估内核实现成本。
B：tanh 近似版0.5x[1 + tanh(√(2/π)(x + 0.044715x³))]。目标模型明确使用 tanh 近似，或精确版经评估不适合作为内核实现时启用。

两种公式不能混用为同一数值合同。若选择 tanh，Golden、测试和文档必须同步切换。

FR-02 Logits 加权前移

  • GELU 流程固定执行 Quant 前加权，Finalize 中不得重复执行。
  • 优先复用当前 topk_weights_type=1 的调度、元数据和通信逻辑。
  • 共享专家是否加权沿用当前规则：共享专家不乘路由权重。
  • 前移后需检查量化输入范围、Scale 分布和精度变化。

D3：旧流程兼容策略 TBD

方案行为影响
A：仅 GELU 固定前移（推荐）GELU 使用 Quant 前加权；现有 SwiGLU 的 type 0/1 行为保持不变。改动范围最小，旧数值合同和回归风险较低。
B：所有激活统一切换默认前移新流程成为默认，旧 GMM2 后加权可暂时保留为兼容选项。流程更统一，但会改变 SwiGLU 默认数值行为，需要额外迁移和回归。

D4：加权与 Quant 之间的数据类型 TBD

方案数据路径启用条件
A：FP32 加权 → BF16 → Quant（推荐）TopK 权重为 FP32，乘法在 FP32 中完成，结果按现有路径转 BF16 后量化。默认继承当前实现，优先验证。
B：FP32 加权结果直接进入 Quant取消加权后的 BF16 中间落地，由 Quant 直接消费 FP32。仅在精度数据证明 BF16 中间舍入不满足要求时启用；需修改 Quant 输入路径并重建 Golden。

FR-03 TopK 最大支持 32

  • 必须覆盖目标 TopK=25，并验证 TopK=32 边界。
  • TopK 索引、权重、元数据、通信、缓冲区、调度和 Finalize 必须共同支持，不允许只放开参数校验。
  • TopK 超出支持范围、专家数不足或索引/权重形状不匹配时，应在执行前明确报错。
  • 两个分支的 TopK 能力定义保持一致。
当前差距：MTE 已允许 TopK≤32；URMA 当前限制为 TopK≤8。是否将 URMA 扩展至 32 属于 D8 的后端范围决策。

FR-04 EP 拓扑

阶段拓扑完成条件
第一阶段8 卡单机完成新流程、精度模式和 TopK25/32 的基础验证。
第二阶段16 卡单机验证 EP 扩展、通信和归并正确性。
第三阶段32 卡跨机验证跨机通信、目标专家配置和完整精度。

核心实现不得固定依赖 8 卡拓扑。各阶段通过不代表后续阶段自动通过，16 卡和 32 卡需分别留存验证结果。

FR-05 A8W4、A8W8

模式逻辑数据类型当前基础目标
A8W4FP8 E4M3 激活 + FP4 E2M1 权重公共 API 已有适配 GELU 和 Quant 前加权。
A8W8FP8 E4M3 激活 + FP8 E4M3 权重公共 API 已有适配 GELU 和 Quant 前加权。

D5：量化格式 TBD

方案规则启用条件
A：全部继承 MX32 + E8M0（推荐）每 32 个元素共享一个 Scale，沿用当前输入、权重和中间 Quant 语义。默认方案，保持两个分支和两种模式的一致性。
B：按目标模型引入其他量化粒度仅针对明确不兼容的模型格式新增配置、数据布局和 Golden。只有目标输入格式证明 MX32 无法直接消费时启用，不作为预先扩展。

FR-07 双场景代码结构

  • 两个分支采用相同的激活类型定义、Logits 顺序、量化语义和配置名称。
  • Golden 的数学公式和舍入顺序保持一致，避免同一输入产生两套参考定义。
  • 必要的平台差异通过适配接口隔离，不复制完整 GMM1—Finalize 流程。
  • 保留 SwiGLU 和既有精度路径的回归验证，防止新增功能改变旧行为。

6. 后端覆盖范围与精度判定

D7：精度阈值 TBD，最迟在最终验收前确定

方案规则建议
A：沿用当前统一 Golden 规则（推荐起步）混合误差阈值 0.01、超限元素不超过 5%、最大混合误差不超过 0.1。先用于 A8W4/A8W8 和新增流程的对比，不在没有数据时预设新阈值。
B：按精度模式分别设阈值根据目标模型、参考实现和实测误差分别定义 A8W4/A8W8 标准。统一规则不适用时启用；新阈值必须在验收前评审，不能为通过测试临时放宽。

D8：MTE / URMA 最终覆盖范围 TBD，详细设计前确定

方案最终范围影响
A：仅目标实际后端完整支持目标后端覆盖 TopK32、EP32、39280 Token；另一后端保留现有限制并明确记录。范围最聚焦，但必须确认目标后端，不能默认 URMA 也满足目标。
B：MTE 与 URMA 均完整支持两种后端都扩展到目标 TopK、EP 和 Token 配置。需要解除 URMA 当前 TopK≤8、EP≤16、Token≤16384 的限制，工作量和验证范围更大。

推荐 先确认目标实际后端，再决定 D8。开发顺序可先在限制较少的路径打通功能，但阶段实现不能代替最终范围承诺。

D9：精度模式与拓扑的组合覆盖 TBD

  • 方案 A（推荐）：最终两种精度模式均覆盖 8 卡、16 卡和 32 卡目标场景。
  • 方案 B：定义明确的支持矩阵，部分模式仅覆盖指定拓扑；必须在交付前公开限制，不能静默跳过组合。

7. 推荐方案组合

推荐基线，不代表已经批准： 标准单路 GELU + 精确 erf 公式 + GELU 固定 Quant 前加权 + FP32 加权后转 BF16 + MX32/E8M0 + 保留现有 SwiGLU 行为 + 先 8 卡再 16/32 卡 + 先沿用当前 Golden 规则。

D1 激活结构标准单路 GELU目标权重为门控结构时改 GEGLU，并重审形状。

D9 组合覆盖两种模式覆盖全部目标拓扑若存在限制，交付明确的支持矩阵。

8. 验证与验收标准

功能与回归

  • GELU 在 GMM1 后执行，公式与 Golden 一致，UBX 与非 UBX 数值语义一致。
  • Logits 在 Quant 前完成，Finalize 无重复加权，共享专家规则保持不变。
  • TopK25 和 TopK32 均通过功能验证，非法 TopK 有明确错误反馈。
  • A8W4、A8W8 均覆盖完整新流程。
  • 现有 SwiGLU 的 type 0/1 及既有精度模式完成回归，不发生非预期行为变化。

拓扑与目标配置

  • 按 8 卡单机、16 卡单机、32 卡跨机分别验证并留存结果。
  • 在最终承诺的后端上，完整运行 39280 Token、800 专家、EP32、TopK25、GMM1 4096/1536、GMM2 1536/4096。
  • 验证工作空间和通信缓冲区无越界、无因固定卡数或固定 TopK 导致的失败。

精度与代码

  • 精度结果满足 D7 最终确认的标准；前移和旧流程分别使用匹配的 Golden。
  • 若采用独立精度阈值，需在测试前固定并记录，不根据单次结果临时调整。
  • 两个分支核心流程和配置保持一致，差异均可追溯到具体平台原因。
  • 记录目标配置性能结果；性能达标值当前为 TBD，不虚构验收指标。
